# ROOTHATCH-FUNCTIONAL-DELIVERY-V1

Adapt the owner's existing engineering discipline, not another project's product
requirements, private records, decision numbers or milestone gates.

## Roles

Parent specifies tasks, admits prerequisites, coordinates one writer, triages
findings, directly verifies results and owns integration. `ironcladexec` implements
specified functionality and causal tests. `ironcladreview` independently checks
functional/specification conformance without editing. `ironcladsecurity` performs
separately scoped defensive checkpoints, findings-only unless a separate bounded
repair assignment is authorized. No offensive work.

## Admission and safety

Use the [six-section template](TASK_TEMPLATE.md). Record `TASK_SCOPE_CHECK: PASS`
only when outcome, requirements, tests, sources, write frontier, effects,
exclusions and checkpoint disposition are concrete. Relevant ordinary source is
available; access is not open-ended assurance authority.

Target identity, permission, validation, safe diagnostics, preservation,
concurrent-writer exclusion and cleanup remain functional tests. Route concrete
incidental defensive concerns to the parent. Block affected demonstrated unsafe
use, not unrelated work by hypothetical association.

## Defensive checkpoints

- Design: path/device/privilege/mount/firmware/VM ownership before privileged implementation.
- Implementation: affected boundary before consequential real-target use.
- Release: public artifacts and privileged runtime before public binaries.

Name target, owner, trigger, actions, status and withheld use for each. Functional
PASS and defensive PASS are independent. Help/version/docs bootstrap does not
require an unrelated host audit and claims no security PASS.

## Lifecycle

Use board `roothatch`. Parent bootstrap cards remain unassigned/non-dispatching.
Bound assigned tasks use same-card implementation -> independent review ->
correction or reviewed completion. Parent acceptance follows actual file/runtime
verification. A distinct security checkpoint has its own bounded card.
No default worker, auto-decomposition, goal loop or autonomous roadmap execution.

Update affected checklist/current-state records and preserve immutable receipts.
Aggregate outcomes are conjunctive, not percentages. Preserve useful partial work
and distinguish product, fixture, environment and metadata failures. Task-approved
in-scope corrections do not need repeated permission. New consequential effects
or materially expanded scope do. Preserve actual refusals/holds; no relabeling,
concealed context or provider/account/route workaround.

## Effects

Workers return tested unstaged changes. Git integration/publication, release,
package installs, root/device/firmware operations, real target data, account
changes and spending require the actual task grant. A role, card or roadmap grants
none implicitly. Keep owner-selected routes/credentials/tool permissions unchanged.
Images, raw operator records and private board exports stay outside public Git.
